# Полное описание фронта DataNorma для реализации в Cursor

## Назначение документа

Этот документ описывает фронтенд сервиса DataNorma: веб-приложения для интеграции и нормализации данных малого и среднего бизнеса. Главный UX-аналог по структуре и логике работы — Airbyte: каталог коннекторов, создание подключений, настройка потоков, запуск синхронизаций, мониторинг, логи и история запусков. При этом визуально DataNorma не должна копировать Airbyte: интерфейс должен быть более спокойным, русскоязычным, с зеленой акцентной палитрой, ориентированной на доверие, чистоту данных и практичность для российского МСП.

Документ нужно использовать как ТЗ для генерации фронтенда в Cursor. При реализации следует воспринимать его как продуктовую спецификацию: сначала собрать каркас навигации и страниц, затем формы и сценарии, затем состояния данных, затем визуальную полировку.

## Контекст продукта

DataNorma — сервис интеграции и нормализации данных для малого и среднего бизнеса. Система позволяет подключать внешние источники данных, выбирать приемники, настраивать сопоставление полей, применять правила нормализации, запускать синхронизации вручную или по расписанию, отслеживать статусы, просматривать журналы и проблемные записи.

Ключевая идея дипломного проекта — не просто передать данные из источника в приемник, а привести данные из разных российских и зарубежных сервисов к единому представлению. Поэтому во фронтенде нужно визуально подчеркнуть не только коннекторы и синхронизации, но и слой нормализации: даты, валюты, единицы измерения, ФИО, телефоны, email, статусы, дубликаты, каноническая модель.

## Основные пользователи и роли

### Администратор платформы

Администратор управляет пользователями, ролями, рабочими пространствами, системными настройками, справочниками нормализации и каталогом доступных коннекторов. Для него важны стабильность, контроль доступа, аудит действий и возможность быстро понять состояние всех интеграций.

### Интегратор данных

Интегратор создает подключения, настраивает источники и приемники, выбирает потоки, сопоставляет поля, задает правила нормализации, запускает sync и разбирает ошибки. Это главный пользователь приложения, поэтому основные сценарии должны быть максимально no-code и пошаговыми.

### Аналитик

Аналитик просматривает результаты загрузки, статусы синхронизаций, нормализованные данные, проблемные записи и историю запусков. Он не обязательно должен иметь доступ к настройке секретов и изменению интеграций.

## Общий UX-принцип

Интерфейс должен быть продуктовым, не академическим. Пользователь должен видеть не “модули системы”, а понятные рабочие сущности: “Подключения”, “Синхронизации”, “Запуски”, “Проблемы данных”, “Нормализация”, “Коннекторы”, “Настройки”.

Основной путь пользователя должен быть таким:

1. Войти в систему.
2. Выбрать рабочее пространство.
3. Открыть каталог коннекторов.
4. Создать источник.
5. Создать приемник.
6. Настроить интеграционный сценарий.
7. Проверить подключение.
8. Выбрать потоки данных.
9. Настроить маппинг и нормализацию.
10. Настроить расписание или ручной запуск.
11. Запустить синхронизацию.
12. Посмотреть статус, логи, ошибки и результат.
13. Исправить ошибки и выполнить повторный запуск.

## Визуальное направление

### Общее ощущение

DataNorma должна выглядеть как надежная B2B-платформа для работы с данными. Визуальный язык: спокойный, чистый, технологичный, но не холодный. Не нужно делать яркий маркетинговый SaaS с крупными градиентами и лишними иллюстрациями. Это рабочий интерфейс, где важны читаемость, плотность информации, предсказуемые состояния и аккуратные детали.

### Отличие от Airbyte

Из Airbyte берем продуктовые паттерны:

- левое боковое меню;
- каталог коннекторов;
- карточки источников и приемников;
- wizard создания connection;
- список connections/syncs;
- статусы запусков;
- run history;
- логи и error detail;
- empty states с явным CTA;
- проверку подключения перед запуском;
- разделение source, destination, connection, stream, sync.

Не копируем:

- фирменные цвета Airbyte;
- визуальные иллюстрации;
- точную структуру компонентов;
- названия, если для русскоязычного пользователя есть более понятный вариант;
- чрезмерно технические формулировки в пользовательском интерфейсе.

### Цветовая система

Основная палитра должна быть зеленой, но не кислотной. Зеленый используется как акцент действия, статуса успешности и смысла “нормализации/очистки”. Нейтральные поверхности должны занимать большую часть интерфейса.

- destructive использовать для ошибок, удаления и критичных failures;
- info использовать для подсказок, preview и системных информационных сообщений;
- фон и панели должны быть нейтральными, с очень мягким зеленым оттенком только в выбранных/активных состояниях;
- нельзя раскрашивать каждую карточку в разные цвета.

### Типографика

Рекомендуемый набор:

- заголовки и UI: `Satoshi`, fallback `Inter`, `sans-serif`;
- моноширинный текст для логов, JSON, SQL, API параметров: `JetBrains Mono`, fallback `monospace`.

Размеры:

- page title: `text-xl`, semibold;
- section heading: `text-lg`, semibold;
- body: `text-sm` или `text-base` в зависимости от плотности экрана;
- table text: `text-sm`;
- badges, metadata, timestamps: `text-xs`;
- не использовать гигантские hero-заголовки внутри приложения.

### Скругления, тени, границы

Интерфейс должен быть плоским и аккуратным:

- базовое скругление: `rounded-md`;
- карточки: `rounded-lg`, тонкая граница `border`;
- тени использовать только для dropdown, modal, popover, toast;
- не делать тяжелые box-shadow на каждой карточке;
- активный элемент меню: мягкий зеленый фон + зеленая левая полоска или акцентная иконка.

### Иконки

Использовать `lucide-react`. Иконки должны помогать сканированию:

- Dashboard: `LayoutDashboard`;
- Connections: `Cable`;
- Sources: `Database`;
- Destinations: `HardDriveDownload` или `Warehouse`;
- Connector catalog: `Plug`;
- Syncs: `RefreshCw`;
- Runs: `Activity`;
- Normalization: `WandSparkles` или `GitMerge`;
- Issues: `CircleAlert`;
- Logs: `FileText`;
- Settings: `Settings`;
- Users: `Users`;
- Help: `CircleHelp`.

Эмодзи не использовать.

## Общая структура приложения

### App shell

Приложение состоит из:

- левого бокового меню;
- верхней панели текущей страницы;
- основной рабочей области;
- правой контекстной панели на сложных экранах;
- нижней служебной зоны в sidebar;
- footer/служебной строки на страницах настроек и документации.

Рекомендуемая структура:

```tsx
<SidebarProvider>
  <div className="flex h-screen w-full bg-background text-foreground">
    <AppSidebar />
    <div className="flex min-w-0 flex-1 flex-col">
      <AppTopbar />
      <main className="min-h-0 flex-1 overflow-auto">
        <PageContent />
      </main>
    </div>
  </div>
</SidebarProvider>
```

Для маршрутизации использовать `wouter` с `useHashLocation`, чтобы маршруты работали после деплоя:

```tsx
<Router hook={useHashLocation}>
  <Switch>
    <Route path="/" component={DashboardPage} />
    <Route path="/connections" component={ConnectionsPage} />
    <Route path="/connections/new" component={ConnectionWizardPage} />
    <Route path="/connections/:id" component={ConnectionDetailPage} />
    <Route path="/runs" component={RunsPage} />
    <Route path="/runs/:id" component={RunDetailPage} />
    <Route component={NotFoundPage} />
  </Switch>
</Router>
```

## Боковое меню

### Верхняя часть sidebar

Вверху sidebar:

- логотип DataNorma;
- название продукта;
- короткий бейдж окружения, например `MVP`, `Demo`, `Local`;
- переключатель рабочего пространства.

Логотип: минималистичный знак из двух пересекающихся потоков данных, которые сходятся в одну нормализованную линию. Можно сделать inline SVG. Цвет логотипа — primary green.

Пример структуры:

```text
[logo] DataNorma
       MVP

Workspace
[ООО Ромашка ▼]
```

Sidebar должен поддерживать:

- раскрытое состояние;
- свернутое состояние только с иконками;
- mobile drawer;
- активный пункт;

- бейдж running рядом с “Запуски”, если есть активные синхронизации.

## Верхняя панель

Topbar находится справа от sidebar и меняется по контексту страницы.

Обязательные элементы:

- breadcrumbs;
- заголовок текущей страницы;
- короткое описание страницы;
- глобальный поиск;
- кнопка быстрого действия;
- индикатор статуса системы;
- notifications;
- avatar menu.

Пример для страницы “Подключения”:

```text
Интеграции / Подключения
Подключения
Настройте сценарии передачи и нормализации данных

[Поиск по подключению, источнику или приемнику] [Создать подключение]
```

### Глобальный поиск

Поиск должен искать по:

- названию connection;
- источнику;
- приемнику;
- connector type;
- run id;
- ошибкам;
- названию stream;
- canonical entity.

Результаты поиска открываются в command palette style popover:

- Connections;
- Runs;
- Issues;
- Connectors;
- Settings.

Горячая клавиша: `Cmd/Ctrl + K`.

## Footer и служебные зоны

У dashboard-приложения не нужен классический маркетинговый footer на каждой странице. Вместо этого нужно использовать две служебные зоны.

### Sidebar footer

Это постоянный footer приложения. Он содержит:

- пользователя;
- роль;
- workspace;
- помощь;
- смену темы;
- выход.

### Page footer

Page footer показывается на страницах настроек, документации, help и audit. Он содержит:

- версию приложения;
- ссылку на API schema;
- время последнего обновления;
- короткую техническую информацию: `DataNorma MVP · API v1 · Europe/Moscow`;
- текст “Данные обрабатываются в рамках выбранного рабочего пространства”.

На рабочих страницах с таблицами footer не нужен, чтобы не мешать плотности интерфейса.

## Главная страница: Дашборд

### Назначение

Дашборд отвечает на вопрос: “Что происходит с интеграциями сейчас и где нужны действия пользователя?”

### Состав экрана

Верхний блок KPI:

- активные подключения;
- успешные запуски за 24 часа;
- запуски с ошибками;
- проблемные записи;
- среднее время sync;
- доля нормализованных записей.

Средний блок:

- график запусков за последние 7 дней;
- stacked bar по статусам: success, partial, failed, running;
- список последних запусков;
- список проблем, требующих внимания.

Нижний блок:

- health по коннекторам;
- “быстрые действия”;
- onboarding checklist, если пользователь новый.

### Быстрые действия

- Создать подключение;
- Добавить источник;
- Добавить приемник;
- Открыть проблемные записи;
- Запустить последний failed sync повторно.

### Empty state

Если интеграций нет:

Заголовок: `Начните с первого подключения`

Текст: `Выберите источник, приемник и настройте правила нормализации. DataNorma проведет вас по шагам.`

CTA:

- primary: `Создать подключение`;
- secondary: `Открыть каталог коннекторов`.

## Страница “Каталог коннекторов”

### Назначение

Каталог помогает пользователю выбрать, какие системы можно подключить. Это один из ключевых экранов, потому что дипломный акцент — готовые коннекторы к российским сервисам.

### Структура

Вверху:

- заголовок;
- поиск;
- фильтры;
- CTA “Запросить коннектор” или “Создать REST-коннектор”.

Фильтры:

- тип: источник, приемник, оба;
- категория: CRM, маркетплейсы, учет, таблицы, файлы, базы данных, реклама, API;
- регион: российские, международные;
- статус: доступен, preview, в разработке;
- способ авторизации: API key, OAuth, login/password, token, file upload.

Карточка коннектора:

- логотип или текстовый знак;
- название;
- категория;
- бейдж `Источник`, `Приемник`, `Preview`;
- краткое описание;
- поддерживаемые потоки;
- статус поддержки;
- кнопка `Настроить`.

Приоритетные коннекторы:

- Ozon;
- Wildberries;
- Яндекс Маркет;
- 1С;
- МойСклад;
- Контур;
- Битрикс24;
- amoCRM;
- VK Реклама;
- Яндекс Метрика;
- Google Sheets;
- CSV;
- XLSX;
- PostgreSQL;
- ClickHouse;
- REST API Builder.

### Детальная страница коннектора

Блоки:

- обзор;
- типы потоков;
- требования к доступу;
- параметры подключения;
- ограничения;
- пример данных;
- поддерживаемая нормализация;
- последние изменения;
- кнопка “Создать источник” или “Создать приемник”.

## Страница “Источники”

### Назначение

Источники — сохраненные подключения к системам, из которых DataNorma извлекает данные.

### Таблица источников

Колонки:

- название;
- коннектор;
- категория;
- статус проверки;
- количество потоков;
- последнее использование;
- владелец;
- действия.

Фильтры:

- по connector type;
- по статусу;
- по владельцу;
- по workspace;
- по дате последней проверки.

Действия:

- посмотреть;
- редактировать;
- проверить подключение;
- создать connection на основе источника;
- удалить.

### Детальная страница источника

Вкладки:

- Обзор;
- Параметры подключения;
- Потоки;
- Проверки;
- Используется в подключениях;
- Журнал изменений.

В overview показать:

- статус подключения;
- последняя проверка;
- доступные streams;
- connections, где источник используется;
- предупреждения по доступу или лимитам API.

## Страница “Приемники”

### Назначение

Приемники — системы или хранилища, куда DataNorma загружает нормализованные данные.

### Таблица приемников

Колонки:

- название;
- тип;
- статус;
- схема/база;
- последнее использование;
- количество подключений;
- действия.

### Поддерживаемые приемники

Для MVP:

## Пользовательские сценарии

### Сценарий 1. Первый вход и создание первого подключения

1. Пользователь открывает `/login`.
2. Вводит email и пароль.
3. После успешного входа попадает на onboarding.
4. Видит checklist и CTA `Создать подключение`.
5. Нажимает CTA.
6. Попадает в wizard.
7. Вводит название connection.
8. Выбирает источник Ozon.
9. Вводит API token.
10. Нажимает `Проверить подключение`.
11. Получает success state.
12. Выбирает streams `orders`, `products`, `stocks`.
13. Выбирает приемник PostgreSQL.
14. Проверяет доступ к приемнику.
15. Запускает auto-map.
16. Исправляет обязательные поля.
17. Включает нормализацию дат, валют, телефонов и дедупликацию.
18. Выбирает incremental sync daily в 03:00 MSK.
19. На финальном шаге видит summary.
20. Нажимает `Сохранить и запустить`.
21. Попадает на run detail.
22. Видит stage timeline и running state.
23. После завершения видит success или partial.

### Сценарий 2. Ошибка подключения к источнику

1. Пользователь выбирает коннектор.
2. Вводит неправильный token.
3. Нажимает `Проверить подключение`.
4. Форма переходит в checking state.
5. Система возвращает failed.
6. Пользователь видит понятное сообщение: `Не удалось подключиться к Ozon. Проверьте API token и Client ID.`
7. Ниже есть раскрываемый блок `Технические детали`.
8. Кнопка `Повторить проверку` доступна после изменения поля.
9. Пользователь исправляет token.
10. Повторяет проверку и идет дальше.

### Сценарий 3. Настройка маппинга

1. Пользователь открывает шаг “Сопоставление полей”.
2. Система показывает поля источника и канонической модели.
3. Auto-map автоматически сопоставляет очевидные поля.
4. Обязательные поля без сопоставления подсвечены warning/error.
5. Пользователь выбирает target field из dropdown.
6. Preview справа показывает исходное и нормализованное значение.
7. При type mismatch система показывает предупреждение.
8. Пользователь выбирает transformation.
9. Нажимает `Сохранить маппинг`.
10. Coverage становится 100% для required fields.

### Сценарий 4. Частичный запуск с проблемными записями

1. Пользователь запускает sync.
2. Extract и staging проходят успешно.
3. Normalize выявляет проблемные записи.
4. Run получает статус `Partial`.
5. Пользователь видит: `Загрузка выполнена частично: 12 140 записей загружено, 37 требуют проверки.`
6. Нажимает `Открыть проблемные записи`.
7. Видит таблицу issues.
8. Открывает issue `invalid phone`.
9. Принимает suggested value или создает правило.
10. Нажимает `Повторить для проблемных записей`.
11. Новый run обрабатывает исправленные строки.

### Сценарий 5. Повторный запуск после ошибки загрузки

1. Run завершается failed на stage `Load`.
2. Пользователь открывает run detail.
3. Error detail объясняет причину.
4. Пользователь нажимает `Открыть маппинг`.
5. Исправляет target field.
6. Возвращается к run или connection.
7. Нажимает `Повторить запуск`.
8. Система создает новый run с ссылкой на предыдущий.
9. В истории видно оба run.

### Сценарий 6. Аналитик просматривает результаты

1. Аналитик входит в систему.
2. Видит dashboard без административных CTA.
3. Открывает `Запуски`.
4. Фильтрует успешные runs за неделю.
5. Открывает нужный run.
6. Смотрит summary и preview данных.
7. Скачивает CSV результата, если роль разрешает export.
8. Не видит секреты подключений и не может редактировать mapping.

### Сценарий 7. Администратор добавляет пользователя

1. Администратор открывает `Пользователи и роли`.
2. Нажимает `Пригласить пользователя`.
3. Вводит email.
4. Выбирает роль `Analyst`.
5. Выбирает workspace.
6. Отправляет приглашение.
7. В audit появляется событие `user.invited`.

### Сценарий 8. Работа с расписанием

1. Интегратор открывает connection.
2. Переходит во вкладку `Настройки`.
3. Включает расписание.
4. Выбирает daily at 03:00 Europe/Moscow.
5. Сохраняет.
6. На странице `Расписания` появляется next run.
7. Пользователь может нажать pause/resume.

### Сценарий 9. Создание REST API коннектора

1. Пользователь открывает каталог коннекторов.
2. Выбирает `REST API Builder`.
3. Вводит base URL.
4. Выбирает auth method.
5. Добавляет endpoint.
6. Настраивает pagination.
7. Указывает path до массива записей.
8. Запускает test request.
9. Видит sample response.
10. Сохраняет как источник.
11. Дальше проходит обычный wizard connection.

### Сценарий 10. Schema drift

1. В источнике появляется новое поле или меняется тип.
2. Следующий run получает warning `schema drift detected`.
3. Connection получает badge `Needs review`.
4. Пользователь открывает вкладку `Маппинг`.
5. Видит новые поля в отдельной группе.
6. Принимает auto-map или игнорирует поле.
7. Сохраняет изменения.
8. Следующий run выполняется без warning.

## Общие состояния интерфейса

### Loading

Для таблиц использовать skeleton rows. Для карточек — skeleton blocks. Для run detail — stage timeline в pending state. Нельзя показывать пустой экран со spinner без контекста.

### Empty

Каждый empty state должен содержать:

- понятный заголовок;
- короткое объяснение;
- primary CTA;
- secondary CTA, если уместно.

### Error

Error state должен быть человекочитаемым:

- что произошло;
- где произошло;
- что сделать;
- технические детали в collapsible блоке.

### Disabled

Disabled элементы должны объяснять причину через tooltip:

- нет прав;
- connection не готов;
- required fields не заполнены;
- source не проверен;
- run уже выполняется.

### Unsaved changes

Если пользователь редактирует mapping, normalization или settings и пытается уйти:

- показать confirmation dialog;
- варианты: `Остаться`, `Выйти без сохранения`, `Сохранить и выйти`.

### Confirmation dialogs

Подтверждение нужно для:

- удаления source/destination/connection;
- остановки running sync;
- сброса mapping;
- отключения расписания;
- изменения роли пользователя.

## Mobile и адаптив

Основной сценарий рассчитан на desktop, потому что настройка интеграций и маппинга требует ширины. Но приложение должно быть usable на планшете и мобильном для мониторинга.

Правила:

- sidebar на mobile превращается в drawer;
- таблицы получают horizontal scroll;
- wizard stepper становится compact;
- mapping table на mobile превращается в карточки полей;
- topbar search скрывается за icon button;
- primary CTA остается видимым;
- log viewer допускает horizontal scroll.

Минимальные breakpoints:

- mobile: `< 768px`;
- tablet: `768–1024px`;
- desktop: `> 1024px`;
- wide: `> 1440px`.

## Доступность

Требования:

- все интерактивные элементы доступны с клавиатуры;
- фокус видимый;
- цвета соответствуют WCAG AA;
- статусы не различаются только цветом, всегда есть текст/иконка;
- формы имеют label и error text;
- dialogs закрываются по Esc;
- destructive actions требуют подтверждения;
- таблицы имеют caption или aria-label;
- skeleton не должен ломать screen reader;
- toast не должен быть единственным местом важного сообщения.

## Microcopy

Тон интерфейса: деловой, ясный, без жаргона там, где это возможно.

Примеры:

- Вместо `Sync failed` писать `Синхронизация завершилась с ошибкой`.
- Вместо `Schema mismatch` писать `Структура данных изменилась`.
- Вместо `Invalid credentials` писать `Не удалось подтвердить доступ. Проверьте ключи подключения.`
- Вместо `Mapping incomplete` писать `Не все обязательные поля сопоставлены`.
- Вместо `Normalize` в кнопке можно писать `Настроить нормализацию`.

## Приемочные критерии фронта

Фронтенд можно считать готовым для демонстрации, если:

- пользователь может пройти путь от создания connection до просмотра run result;

- wizard содержит шаги source, destination, streams, mapping, normalization, schedule, review;
- connection detail показывает overview, streams, mapping, normalization, runs, logs, issues;

- issues page позволяет понять проблемы нормализации;

- есть empty, loading, error и disabled states;
- интерфейс русскоязычный;
- таблицы и формы имеют стабильные `data-testid`;
- приложение работает в light и dark mode;
- mobile layout не ломается.
